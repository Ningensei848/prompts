# 親エージェント向けプロンプトの取扱説明書

## 1. この文書の位置づけ

この文書は、Microsoft Copilot Studio において教育支援用の「親エージェント（全体の司令塔）」を実装・保守するための取扱説明書である。

別紙の「親エージェント向けプロンプト最終版」は、Copilot Studio の Instructions 欄に貼り付ける実装用プロンプトである。

本書は、プロンプトそのものではなく、以下を説明するための運用ドキュメントである。

- 最終版プロンプトの設計思想
- あえて削った内容とその理由
- Copilot Studio 上での実装上の注意
- 子エージェント Description の設計方針
- 親エージェントと子エージェントの責任分界
- テスト観点
- 保守・改訂時の判断基準

---

## 2. 親エージェントの基本設計思想

この親エージェントは、「ユーザーと直接会話する唯一の窓口」である。

一方で、親エージェント自身は専門講師ではない。専門的な説明、演習、添削、採点、評価、リサーチ、学習計画の作成は、対応する専門子エージェントに委任する。

つまり、親エージェントの責務は次の4つである。

1. ユーザーの学習意図を判定する。
2. 適切な子エージェントへ処理を委任する。
3. 子エージェントの出力を統合・整形する。
4. ユーザーに自然な1つの回答として返す。

この設計では、Single Response Principle を重視する。

ユーザーに対して複数のエージェントが別々に発話しているように見せてはならない。ユーザーから見える会話主体は、常に親エージェント1体である。

---

## 3. なぜ親エージェントに専門回答させないのか

親エージェントが専門知識を直接回答してしまうと、以下の問題が発生する。

- 子エージェントやRAGの存在意義が薄れる。
- ナレッジソースに基づかない回答が混入する。
- 専門領域ごとの教育方針が統一されない。
- ルーティング精度の検証が難しくなる。
- 子エージェント側の改善効果が親の直接回答に埋もれる。
- 回答の責任境界が曖昧になる。

したがって、親エージェントは「専門回答を作る存在」ではなく、「専門回答を取り寄せ、学習者向けに整える存在」として設計する。

親エージェントが直接対応してよいのは、挨拶、利用案内、学習テーマの確認、対応外依頼への誘導、子エージェント出力の統合、会話要約、セッション終了案内などに限定する。

---

## 4. 最終版プロンプトを短縮版にした理由

当初の統合版は、設計書としては妥当だったが、Copilot Studio の Instructions 欄にそのまま貼り付けるには長すぎる可能性があった。

そのため、最終版では「運用ルール中心の短縮版」とした。

短縮版では、次の中核ルールを残している。

- ユーザーに直接応答するのは親エージェントのみ。
- 専門回答は必ず対応する子エージェントに委任する。
- 子エージェントの生出力をそのまま見せない。
- 存在しない子エージェントを仮定しない。
- 接続されている子エージェントの Description を最優先する。
- 曖昧な依頼では確認質問を原則1つだけ行う。
- 対応外依頼では親が専門回答せず、対応可能領域へ誘導する。
- ターン数上限に近い場合は、新規委任より要約と終了を優先する。

これらは、親エージェントの挙動を安定させるための最小限の制御ルールである。

---

## 5. 削った内容とその理由

### 5.1 判断例の大半を削った理由

長い判断例は、設計意図を理解するには有用である。

しかし、Instructions 欄に多数の例を入れると、以下の問題が発生する。

- 文字数上限を圧迫する。
- 例に引きずられ、未知のケースで柔軟性が落ちる。
- 実際の子エージェント構成と例がズレる可能性がある。
- プロンプト保守時に、例の更新漏れが発生しやすい。

そのため、最終版では判断例を最小限にし、運用ルールを優先した。

判断例は、Instructions 本体ではなく、テストケースまたは運用ドキュメント側に持たせるほうがよい。

---

### 5.2 禁止事項・必須事項・最重要ルールの重複を削った理由

当初案では、禁止事項、必須事項、最重要ルールに似た内容が重複していた。

重複は、人間が読む設計書としては強調効果があるが、実装プロンプトとしては以下の問題がある。

- 文字数を消費する。
- モデルに同じ制約を何度も読ませることになる。
- 似ているが微妙に異なる表現があると、解釈の揺れを生む。
- 後から修正する際、片方だけ直して不整合が起きる。

最終版では、重要ルールを「基本原則」「ルーティング判断」「最重要ルール」に整理し、重複を減らした。

---

### 5.3 子エージェントに渡す情報の長い列挙を圧縮した理由

子エージェントに渡すべき情報を詳細に列挙すること自体は有効である。

しかし、親エージェントの Instructions に過度に長く書くと、ルーティングと統合という本来の役割がぼやける。

そのため、最終版では次の程度に圧縮した。

- ユーザーの原文
- 推定テーマ
- 目的
- 理解度
- 会話履歴
- 制約条件
- 出力形式
- 注意文脈
- 期待する教育支援形式

実装上は、必要に応じてトピック、変数、Power Fx、フロー、子エージェント側 Instructions で補う。

---

### 5.4 トーンの細かい列挙を削った理由

教育支援エージェントでは、トーンは重要である。

ただし、トーン指定を細かく書きすぎると、以下の問題がある。

- Instructions の文字数を圧迫する。
- ルーティングや委任の制御よりも文体指定が目立ってしまう。
- 実装者がプロンプトの本質を把握しづらくなる。

最終版では、トーンを次の方針に圧縮している。

- 落ち着いている
- 明確である
- 学習者を責めない
- 次の行動がわかる
- 過度にくだけすぎない
- 質問攻めにしない

詳細な文体調整は、必要に応じて子エージェント側またはチャネル別の応答テンプレートで管理する。

---

## 6. 最終版プロンプトの妥当性

最終版プロンプトは、次の点で妥当である。

### 6.1 Copilot Studio の親子構成に合っている

親エージェントは、子エージェント、トピック、ツール、ナレッジを選択する司令塔として機能する。

そのため、親エージェントの Instructions には、専門知識そのものではなく、ルーティング、委任、統合、対応外処理、終了条件を書くのが適切である。

### 6.2 Description 依存の設計になっている

Copilot Studio では、接続されている子エージェントやツールを選択する際、名前や Description が重要になる。

したがって、親エージェントのプロンプト内に固定的な子エージェント一覧を書き込むより、実際に接続されている子エージェントの Description を最優先する設計のほうが安全である。

### 6.3 存在しない能力を仮定しない

親エージェントが、実際には存在しない子エージェントやナレッジソースを仮定すると、ユーザーに誤った期待を与える。

最終版では「存在しない子エージェントを仮定しない」と明記しているため、実装上の安全性が高い。

### 6.4 専門回答の責任境界が明確である

専門回答は子エージェントに委任し、親エージェントは統合・整形に徹する。

これにより、専門領域ごとの改善、ナレッジ更新、評価、テストがしやすくなる。

### 6.5 会話の肥大化を抑制している

教育支援エージェントは、ソクラテス式問答を強くしすぎると、会話が長期化しやすい。

最終版では、ターン数上限に近い場合は新しい委任を避け、要約と終了に向かうよう定義している。

## 7. Copilot Studio 実装時の注意

## 7.1 Instructions 欄の文字数を管理する

Copilot Studio の Instructions 欄には文字数上限がある。

最終版プロンプトは、上限ぎりぎりではなく、余裕を持った文字数にすること。

推奨運用は以下である。

- Instructions 本体は 6,500〜7,000文字程度を目安にする。
- 8,000文字ぎりぎりまで使わない。
- 後から追記する余白を残す。
- 外側のコードフェンス、見出し装飾、説明文は貼り付けない。
- 貼り付け後に保存できるか必ず確認する。

---

## 7.2 子エージェントの Description を丁寧に書く

親エージェントのルーティング精度は、子エージェントの Description に大きく依存する。

各子エージェントの Description には、少なくとも以下を含める。

- 対象領域
- 扱える質問
- 扱えない質問
- 参照する教材・ナレッジ
- 想定する学習者レベル
- 典型的な委任例
- 他の子エージェントとの違い

悪い Description の例：

「教育用のボットです。何でも教えます。」

良い Description の例：

「Excel の関数、表計算、ピボットテーブル、Power Query、VLOOKUP/XLOOKUP、業務データ分析に関する教材を参照し、学習者の理解度に合わせて段階的に説明・演習・確認質問を行う専門チューターです。英語、プログラミング、一般的なビジネス文書作成は対象外です。」

---

## 7.3 子エージェントのナレッジを重複させすぎない

複数の子エージェントに同じナレッジソースを広く紐付けると、親エージェントが委任先を迷いやすくなる。

特に、以下のような重複は避ける。

- Excel子エージェントとビジネススキル子エージェントの両方に同じ「業務資料全般」を入れる。
- 英語子エージェントとビジネス文書子エージェントの両方に同じ「メール文例集」を入れる。
- プログラミング子エージェントとデータ分析子エージェントの両方に同じ「Python教材」を無差別に入れる。

重複が必要な場合は、Description 上で役割差を明確にする。

例：

- 英語子エージェント：英語表現、文法、自然さを評価する。
- ビジネススキル子エージェント：資料構成、目的整理、説得力を評価する。

---

## 7.4 親エージェントには詳細教材を持たせすぎない

親エージェントに教材や専門知識を持たせすぎると、親が直接専門回答しやすくなる。

親エージェントに持たせるべきなのは、以下である。

- ルーティング方針
- 委任方針
- 出力統合方針
- 対応外処理
- セッション終了条件

教材、FAQ、専門手順、演習問題、採点基準は、原則として子エージェント側または子エージェントのナレッジに置く。

---

## 7.5 ターン数制御はプロンプトだけに頼らない

「会話が長くなったら終了へ向かう」という指示だけでは、会話が長引いた場合に制御が不安定になる可能性がある。

そのため、Copilot Studio 側で以下を実装する。

- ユーザー発話ごとに `State.NumOfTurns` を加算する。
- 一定回数に達したら、子エージェント委任を止める。
- 上限に達したら、要約メッセージを返す。
- 必要に応じて End of conversation トピックへ遷移する。

推奨例：

- 4ターン目：要点整理を促す。
- 5ターン目：新しい分岐や追加演習を避ける。
- 6ターン目：セッションを終了方向へ進める。

この回数は、実際の教育設計に合わせて調整してよい。

---

## 7.6 生成回答ノードのカスタム指示を増やしすぎない

親エージェントの Instructions に加えて、生成回答ノードにも長いカスタム指示を書くと、全体のプロンプト量が増え、内部上限や応答品質に影響する可能性がある。

生成回答ノード側のカスタム指示は、次のような短い用途に限定する。

- そのノード固有の回答形式
- 特定トピックでの禁止事項
- 特定ナレッジの使い方
- その場限りの出力制約

親エージェント全体に関わるルールは、親エージェントの Instructions に集約する。

---

## 7.7 複数子エージェント委任は例外扱いにする

複数領域にまたがる質問では、複数の子エージェントに委任したくなる。

しかし、複数委任は以下の問題を生みやすい。

- 応答が遅くなる。
- 出力が冗長になる。
- 子エージェント同士の観点が衝突する。
- 親エージェントの統合負荷が高くなる。
- ユーザーの主目的から外れやすくなる。

原則として、まず主目的に最も近い子エージェントを1つ選ぶ。

複数委任は、1つの子エージェントだけでは明らかに不十分な場合に限定する。

---

## 7.8 対応外領域では親が専門回答しない

対応外領域では、親エージェントが一般知識で回答してしまわないようにする。

特に注意すべき領域は以下である。

- 医療
- 法律
- 投資
- 税務
- 個人情報
- セキュリティ事故
- ハラスメント
- 採用・人事評価
- 高リスクな意思決定

対応する専門子エージェントがない場合は、専門助言を避け、対応可能な学習領域へ誘導する。

---

## 7.9 公開前に必ずテストする

親エージェント公開前に、最低限以下のテストを行う。

### ルーティングテスト

- Excelの質問がExcel系子エージェントに委任されるか。
- 英語の質問が英語系子エージェントに委任されるか。
- プログラミングの質問がプログラミング系子エージェントに委任されるか。
- ビジネススキルの質問がビジネススキル系子エージェントに委任されるか。
- 複数領域の質問で、主目的に近い子エージェントが選ばれるか。

### 曖昧入力テスト

- 「勉強したい」
- 「資料をよくしたい」
- 「これがわからない」
- 「表が変」
- 「英語で説明したい」

これらに対して、親が無理に専門回答せず、確認質問を1つだけ行うかを確認する。

### 対応外テスト

- 投資助言
- 医療相談
- 法律相談
- 個人情報を含む相談
- 子エージェントが存在しない領域の質問

これらに対して、親が専門回答せず、対応可能領域へ誘導するかを確認する。

### Single Response Principle テスト

- 子エージェント名を不必要に表示しないか。
- 「子エージェントの回答です」と言わないか。
- 子エージェントの生出力を貼り付けないか。
- 複数エージェントが話しているように見えないか。

### ターン数テスト

- 4〜5ターン目で要約に向かうか。
- 6ターン目以降で新しい分岐を避けるか。
- End of conversation への遷移が機能するか。

---

## 8. 子エージェント側で整備すべきもの

親エージェントだけでは、教育支援ソリューションは完成しない。

子エージェント側では、少なくとも以下を整備する。

### 8.1 Description

親エージェントがルーティング判断に使うため、短く明確に書く。

含めるべき内容：

- 専門領域
- 対象範囲
- 対象外範囲
- 使用する教材・ナレッジ
- 学習者レベル
- 出力形式
- 他の子エージェントとの違い

### 8.2 Instructions

子エージェント自身の教育方針を書く。

含めるべき内容：

- 専門チューターとしての役割
- 教材・ナレッジの使い方
- ソクラテス式問答の使い方
- 解説とヒントの切り替え基準
- 演習作成の方針
- 添削・評価の基準
- 親エージェントに返す出力形式

### 8.3 Knowledge

専門領域ごとに、必要な教材や業務ナレッジを接続する。

注意点：

- 他の子エージェントと重複させすぎない。
- 古い教材を放置しない。
- 教材の対象範囲を明確にする。
- ユーザーに見せてよい情報だけを含める。

---

## 9. 推奨する子エージェント Description テンプレート

子エージェントの Description は、以下の形式で作成するとよい。

```text
[専門領域]に関する教育支援を行う専門チューターエージェントです。
主に[対象トピック]を扱い、[教材・ナレッジ]を参照して、学習者の理解度に合わせた説明、ヒント、演習、添削、確認質問を提供します。
[対象外トピック]は扱いません。
このエージェントは、ユーザーが[典型的な依頼例]を求めた場合に使用してください。
```

例：

```text
Excelの関数、表計算、ピボットテーブル、Power Query、VLOOKUP/XLOOKUP、業務データ分析に関する教育支援を行う専門チューターエージェントです。
Excel教材と業務データ分析マニュアルを参照して、学習者の理解度に合わせた説明、ヒント、演習、確認質問を提供します。
英語学習、プログラミング一般、プレゼン資料構成、投資助言は扱いません。
このエージェントは、ユーザーがExcel操作、関数、集計、データ整理、表計算の学習支援を求めた場合に使用してください。
```

---

## 10. 保守・改訂時の判断基準

親エージェントのプロンプトを改訂する場合は、以下の基準で判断する。

### 追加してよい内容

- ルーティング精度を上げるルール
- 対応外依頼への安全な誘導
- 子エージェントとの責任分界を明確にする記述
- ターン数制御に関する短いルール
- ユーザー体験を大きく改善する短い応答方針

### 追加しないほうがよい内容

- 専門知識そのもの
- 長い判断例
- 個別教材の詳細
- 子エージェント側に書くべき教育方針
- トーンの細かすぎる指定
- 同じ禁止事項の重複
- 実際には存在しない子エージェント名

### 削るべきサイン

- Instructions が 7,000文字を超えている。
- 似たルールが複数箇所にある。
- 親エージェントが専門回答しやすくなっている。
- 子エージェント Description と矛盾している。
- 実装済みトピックやフローで制御している内容を、プロンプトにも長く書いている。
- テスト時に、親が子エージェントを使わずに専門回答している。

---

## 11. 推奨する実装順序

実装は次の順序で進める。

1. 子エージェントの専門領域を決める。
2. 子エージェントごとの Knowledge を分ける。
3. 子エージェントごとの Description を作る。
4. 子エージェントごとの Instructions を作る。
5. 子エージェントを公開し、親エージェントから接続可能にする。
6. 親エージェントの Instructions に最終版プロンプトを設定する。
7. 親エージェント側でターン数カウンターを実装する。
8. ルーティングテストを行う。
9. 曖昧入力、対応外入力、複数領域入力をテストする。
10. 問題があれば、まず子エージェント Description を修正する。
11. それでも改善しない場合のみ、親エージェント Instructions を修正する。

---

## 12. 実装後の評価観点

運用開始後は、以下の観点でログやテスト結果を確認する。

### 12.1 ルーティング品質

- 適切な子エージェントが選ばれているか。
- 複数領域の質問で主目的を外していないか。
- 対応外領域に無理に答えていないか。
- 曖昧な質問で確認質問を行っているか。

### 12.2 回答品質

- 子エージェントの出力を自然に統合できているか。
- 学習者にとって次の行動が明確か。
- 説明が長すぎないか。
- 質問攻めになっていないか。
- 子エージェント名や内部処理を不必要に見せていないか。

### 12.3 セッション制御

- ターン数が増えたときに要約へ向かっているか。
- 新しい分岐を増やし続けていないか。
- セッション終了時に次の学習ステップを提示できているか。

### 12.4 保守性

- 親プロンプトが長くなりすぎていないか。
- 子エージェント Description と親プロンプトが矛盾していないか。
- ナレッジソースの重複でルーティングが不安定になっていないか。
- 子エージェントを追加したときに親プロンプトを大幅変更せずに済むか。

---

## 13. まとめ

親エージェントのプロンプトは、教育コンテンツそのものを書く場所ではない。

親エージェントの Instructions に書くべきなのは、以下である。

- 誰がユーザーに返答するか
- 専門回答を誰に委任するか
- どの情報を優先してルーティングするか
- 子エージェント出力をどう統合するか
- 曖昧な依頼や対応外依頼をどう扱うか
- 会話が長くなったときにどう終えるか

教材、専門知識、演習、添削基準、分野固有の教育方針は、子エージェント側に置く。

親エージェントは、専門家ではなく司令塔である。

この責任分界を守ることが、Copilot Studio におけるマルチエージェント型教育支援ソリューションの安定性、拡張性、保守性を高める。
